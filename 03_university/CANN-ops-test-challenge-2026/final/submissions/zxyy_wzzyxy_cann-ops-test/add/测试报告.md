# Add 算子测试报告

> 测试环境：Ascend 910_93，CANN 工具链，--soc=ascend910_93（真机）

---

## 一、算子理解

Add 算子执行逐元素加法，数学定义为：

$$y_i = x1_i + \alpha \times x2_i$$

其中 $\alpha$ 为标量缩放因子（默认为 1）。支持 broadcasting，当两个输入 shape 不一致时按广播规则对齐后逐元素计算。

**支持的数据类型**（aclnn_add.cpp 中按 SOC 版本区分）：

- ascend910_93（DAV_3510/DAV_2201）：FLOAT32、FLOAT16、BF16、INT32、INT64、INT16、INT8、UINT8、DOUBLE、BOOL、COMPLEX64、COMPLEX128
- 混合类型：FP16+FP32、FP32+FP16、BF16+FP32、FP32+BF16

**6 个 API 变体**：

| API               | 语义                                   |
| ----------------- | ------------------------------------ |
| aclnnAdd          | tensor + alpha * tensor              |
| aclnnAdds         | tensor + alpha * scalar              |
| aclnnInplaceAdd   | selfRef += alpha * tensor（原地）        |
| aclnnInplaceAdds  | selfRef += alpha * scalar（原地）        |
| aclnnAddV3        | scalar + alpha * tensor（V3，self 为标量） |
| aclnnInplaceAddV3 | V3 原地版本                              |

**关键执行路径**（aclnn_add.cpp 中的分支）：

1. isMixDataType=true + alpha=1 → 直接 Add（混合 dtype 路径）
2. 同 dtype + alpha=1 → 直接 Add
3. 不同 dtype + alpha=1 → Cast + Add
4. alpha≠1 + promoteType 在 Axpy 列表（FLOAT/INT32/FP16）→ Axpy 融合算子
5. alpha≠1 + promoteType 在 AxpyV2 列表（RegBase 架构）→ AxpyV2
6. 其他 → Mul + Add

## 二、测试策略与用例设计

### 测试方法

采用端到端测试，在真实 NPU 上执行，CPU 端以 double 精度计算 Oracle 进行数值比对。

**Oracle 选择**：所有浮点场景的 CPU 参考均使用 double 精度计算已量化的输入值（`(double)x1[i] + alpha * (double)x2[i]`），确保参考基准与 NPU 输入一致。

**FP16 特殊处理**：FP16 数据以 `uint16_t` 存储，CPU Oracle 通过 `Fp16ToFloat`/`FloatToFp16` 编解码，不直接用 `uint16_t` 做 C++ 运算（否则会把位模式当整数计算，产生巨大误差）。

**INT32 溢出 Oracle**：使用无符号路径 `(int32_t)((uint32_t)a + (uint32_t)b)` 避免有符号溢出 UB。

### 精度容差

| dtype                       | atol | rtol |
| --------------------------- | ---- | ---- |
| FLOAT32                     | 1e-6 | 1e-6 |
| FLOAT16                     | 1e-2 | 1e-2 |
| BF16                        | 1e-2 | 1e-2 |
| INT32/INT64/INT8/UINT8/BOOL | 精确匹配 | 精确匹配 |

## 四、精度分析

所有浮点场景的 CPU 参考均以 double 精度计算已量化的 Float32 输入。

### 场景一：大数吞没小数（TC43）

**测试输入**：self=[1e10, 1e10]，other=[1e-5, 1e-5]，alpha=1.0，dtype=FLOAT32

**分析**：FP32 约有 7 位十进制有效数字。1e10 与 1e-5 相差 15 个数量级，远超 FP32 的精度范围。在 FP32 表示中，1e10 的 ULP 约为 1024，远大于 1e-5，因此小数被完全吞没，结果等于 1e10。

**实测**：NPU 输出 1e10，期望值 10000000000.00001，绝对误差约 1e-5。

**风险**：在需要累加大量不同量级数值的场景（如神经网络中的 loss 累加），小梯度分量会被大值吞没，导致训练停滞。

### 场景二：正负抵消（TC44）

**测试输入**：self=[1.0000001, 2.0000001]，other=[-1.0, -2.0]，alpha=1.0，dtype=FLOAT32

**分析**：FP32 在 1.0 附近的 ULP 约为 1.19e-7。1.0000001 与 1.0 的差值（1e-7）正好处于这一量级，量化为 FP32 时已存在约 1.49e-8 的量化误差。相减后理论结果约为 1e-7，但 FP32 的精度已无法可靠表示这一差值，发生灾难性消除（Catastrophic Cancellation）。

**风险**：在迭代算法中，当两个接近的值相减时，有效位数急剧减少，可能导致收敛判据失效。

### 场景三：alpha 参数引入的额外误差（TC45）

**测试输入**：self=[1.0, 2.0, 3.0]，other=[0.1, 0.2, 0.3]，alpha=3.14159f

**分析**：alpha=3.14159f 是 π 的近似值，存储为 FP32 时量化误差约为 2.65e-7（相对于数学 π）。这个量化误差会乘以 other[i] 后叠加到最终结果中。对于 other[i]=0.3，alpha 量化误差引入的额外误差约为 7.95e-8，在 FP32 容差范围内。

**结论**：alpha 量化误差对单次运算影响较小（约 1e-7 量级），但在迭代计算中可能累积。

### 场景四：混合类型运算精度损失（TC46）

**测试输入**：self 为 FP16 tensor，other 为 FP32 tensor，alpha=1.0

**分析**：FP16 只有 10 位尾数，机器精度 ε ≈ 9.77e-4，十进制有效位数约 3 位。FP32 输入量化为 FP16 时已损失精度（如 1.234567f 量化为 FP16 后约为 1.234375）。混合 dtype 加法的结果精度受限于精度较低的 FP16 输入。

**实测**：FP16+FP32 与 FP32+FP32 的结果差异约为 1e-3 量级，与 FP16 精度标称值一致。

**风险**：在混合精度训练中，FP16 的精度损失可能导致梯度更新不准确，需要配合损失缩放（Loss Scaling）技术。

### 场景五：浮点特殊值处理（TC47-TC49）

**上溢（TC47）**：3.4e38 + 3.4e38 超出 FP32 最大有限值（3.4028235e38），按 IEEE 754 标准映射为 +Inf。验证使用 `std::isinf` 而非有限 atol。

**NaN 传播（TC48）**：NaN + 任何值 = NaN，符合 IEEE 754 标准。NaN 具有强传染性，一旦出现会污染后续所有计算。

**次正规数（TC49）**：1e-38 + 1e-38 = 2e-38，接近 FP32 最小正规数（1.175e-38），结果为正规数。次正规数区间的精度随量级减小而降低，且不同硬件配置下可能启用 FTZ（Flush-to-Zero）模式将次正规数归零。

### 场景六：INT32 溢出行为（TC50-TC51）

**正向溢出（TC50）**：INT32_MAX + 1 = INT32_MIN（-2147483648），按二进制补码低 32 位截断。

**负向溢出（TC51）**：INT32_MIN + (-1) = INT32_MAX（2147483647），同样按补码回绕。

**注意**：C++ 标准中有符号整数溢出是 UB，Oracle 实现使用无符号路径 `(int32_t)((uint32_t)a + (uint32_t)b)` 避免 UB。NPU 的实际行为与无符号回绕一致。

## 五、反思与改进

**关键改进点**：

1. 覆盖了 aclnn_add_v3.cpp（V3 API），避免了 MUL 样例中 0% 覆盖率的问题
2. 覆盖了 add_tiling_arch35.cpp 的全部 10 个 dtype 分支，需要 CMakeLists 补丁配合
3. FP16 Oracle 使用正确的编解码方式，避免了位模式误用
4. INT32 溢出 Oracle 使用无符号路径，避免了 UB

**潜在改进方向**：

- COMPLEX64/COMPLEX128 的完整验证（当前仅测试 GetWorkspaceSize 返回值）
- 非连续 tensor（stride≠1）的测试，触发 Contiguous 路径
- 更大 tensor（如 1024×1024）的性能与精度测试
- DOUBLE 类型的测试（若平台支持 AiCpu 路径）

**方法论收获**：

- Oracle 本身的正确性需要单独验证，FP16 位模式误用是常见陷阱
- 精度分析中"误差"的含义依赖参照对象（相对 CPU double 参考 vs 相对数学真值）
- 覆盖率的关键不在于用例数量，而在于系统性地识别并触发每个代码分支
