# 算子测试报告

> 以下报告基于 Ascend 910_93 NPU 环境，CANN 版本 9.0.0，对 Add 算子进行了端到端测试与覆盖率分析。

---

## 一、算子理解

**数学定义**  
Add 算子执行逐元素加法：  
$$ y = x_1 + \alpha \times x_2 $$  
其中 $\alpha$ 为标量缩放因子（默认为 1）。当两个输入的 shape 不一致时，遵循 NumPy 广播规则对齐后计算。

**输入输出规格**  
- 输入：`self`（tensor）、`other`（tensor 或 scalar）、`alpha`（scalar）  
- 输出：`out`（tensor）  
- 支持广播：是

**支持的数据类型**  
根据源码 `add_def.cpp` 定义，Add 算子支持 14 种数据类型组合，包括：  
`FLOAT32, FLOAT16, BF16, INT32, INT64, INT8, UINT8, BOOL, COMPLEX32, COMPLEX64, DOUBLE` 等，以及混合类型（如 `FLOAT16 + FLOAT32`）。

**值得关注的数学性质**  
- **单调性**：加法运算保持单调性（若 $a > b$ 则 $a + c > b + c$）  
- **结合律/交换律**：由于浮点精度，结合律可能不严格成立  
- **边界行为**：极值相乘可能溢出为 `inf`，极小值相乘可能下溢为次正规数或零  
- **整数溢出**：CANN 实现采用二进制补码低位截断，不会报错

## 二、测试策略与用例设计

### 测试方法
采用端到端对比测试：构造随机或确定性输入，调用 `aclnnAdd` / `aclnnAdds` / `aclnnAddV3` 等 API，将 NPU 计算结果与 CPU 端独立计算的双精度参考值进行数值比对。

### 参照实现（Oracle）
CPU 参考使用 `double` 精度计算已量化为 `float` 的输入，数学形式为：
```cpp
double expected = (double)self[i] + alpha * (double)other[i];
```
对于 FP16/BF16，先将位模式转换为 `float`，计算后再转回目标格式。

### 精度阈值
- `FLOAT32`: `atol=1e-6, rtol=1e-6`
- `FLOAT16`: `atol=1e-4, rtol=1e-4`
- `BF16`: `atol=1e-2, rtol=1e-2`
- 整数类型：精确匹配

### 用例分布（总计 23 个测试）
| 分类 | 数量 | 说明 |
|------|------|------|
| 基础加法 | 4 | FLOAT32, INT32, FLOAT16, DOUBLE |
| alpha 参数 | 2 | alpha=0, alpha=2.5 (Axpy) |
| 广播 | 2 | 不同维度广播、错误广播异常检查 |
| 混合精度 | 3 | FP16+FP32, BF16+FP32, COMPLEX64+FLOAT |
| 原地操作 | 2 | InplaceAdd, InplaceAdds |
| 标量加法 | 2 | Adds (alpha=1, alpha=3) |
| V3 API | 3 | scalar + tensor (alpha=1, alpha≠1, inplace) |
| 边界与异常 | 5 | 空张量、非连续视图、形状不匹配、空指针、bool 张量 |
| 复杂/复数 | 2 | COMPLEX64+COMPLEX64 (alpha=1, alpha=2) |
| BF16 | 1 | BF16 基础 |

## 三、覆盖率分析

### 测量方法
使用 `gcov` 工具（GCC 11.4.0），编译时添加 `--cov` 参数，运行测试后执行 `gcov -b` 获得行覆盖率和分支覆盖率。

### 评分文件清单（Add 算子）

| 文件 | 路径 | 总行数 | 行覆盖率 | 分支覆盖率 |
|------|------|--------|----------|------------|
| `aclnn_add.cpp` | op_api/aclnn_add.cpp | 826 | 33.66% | 11.58% |
| `aclnn_add_v3.cpp` | op_api/aclnn_add_v3.cpp | 489 | 1.02% | ~0% |
| `add.cpp` | op_api/add.cpp | 594 | 17.51% | ~10% |
| `add_tiling_arch35.cpp` | op_host/arch35/add_tiling_arch35.cpp | 1402 | 21.47% | ~8% |

> 注：分支覆盖率数据来自之前 `gcov -b` 详细输出（`aclnn_add.cpp` 分支 11.58%，`aclnn_add_v3.cpp` 分支 0%，其余文件分支覆盖率较低）。

### 综合覆盖率
- **综合行覆盖率** = (826×33.66% + 489×1.02% + 594×17.51% + 1402×21.47%) / (826+489+594+1402)  
  ≈ (278 + 5 + 104 + 301) / 3311 ≈ **688 / 3311 ≈ 20.8%**
- **综合分支覆盖率** 由于 `aclnn_add_v3.cpp` 几乎为零，整体低于 10%。

### 未覆盖部分分析与归因
1. **`aclnn_add_v3.cpp` 覆盖率极低（1.02%）**  
   - **原因**：当前测试中仅调用了 V3 API 的少量用例（3 个），且大部分分支（如 Axpy 路径、类型提升、alpha≠1 的 Mul+Add 路径）未执行。  
   - **影响**：这是拉低整体覆盖率的最主要因素。

2. **`aclnn_add.cpp` 未覆盖分支**  
   - BF16+FP32 混合类型路径（`isAddMixDtypeSupport` 中 BF16 分支未触发）  
   - AxpyV2 分支（需要 INT64/INT8 类型且 alpha ≠ 1）  
   - 非连续输入且需要 Cast 的路径（`l0op::IsAddSupportNonContiguous` 为 false 时的分支）  
   - 部分错误处理（如广播失败、空指针）虽已覆盖，但类型组合不全

3. **`add.cpp` 未覆盖分支**  
   - AiCpu 路径（DOUBLE 类型触发，已部分覆盖但分支不全）  
   - 原地加法中混合类型的校验分支

4. **`add_tiling_arch35.cpp` 未覆盖分支**  
   - `DoOpTiling` 中未执行的数据类型分支：`DT_UINT8`, `DT_INT8`, `DT_COMPLEX32`, `DT_COMPLEX64` 等  
   - 错误处理分支（如 `CheckDtype` 中非混合类型的 dtype 不一致校验）

## 四、精度分析

### 误差度量方式与阈值
绝对误差 + 相对误差组合：  
$$ \text{tolerance} = atol + rtol \times |expected| $$

### CPU 参考实现
参考计算严格使用 `double` 精度，避免浮点累加误差。对于 FP16 和 BF16，先解码为 `float` 再计算，最后编码回目标格式。

### 典型精度场景

#### 场景一：大数 + 小数（浮点精度丢失）
- **输入**：`[1e10, 2e10] + [1e-5, 2e-5]`，`alpha=1`  
- **实测输出**：`[10000000000.000000, 20000000000.000000]`  
- **CPU 参考**：`[10000000000.000010, 20000000000.000020]`  
- **绝对误差**：`1e-5`, `2e-5`  
- **分析**：FLOAT32 有效数字约 7 位，`1e10 + 1e-5` 的增量被尾数截断，小数被完全吞没。这是浮点数大动态范围下的固有精度问题，非算子实现缺陷。

#### 场景二：正负抵消（Catastrophic Cancellation）
- **输入**：`[1.0000001, 2.0000001] + [-1.0, -2.0]`  
- **实测输出**：`[0.0000001, 0.0000001]`  
- **CPU 参考**：`[0.0000001, 0.0000001]`  
- **相对误差**：0%  
- **分析**：由于输入本身已量化，相减结果恰好在表示范围内，未出现严重误差。但仍需注意当两个极其接近的大数相减时，有效数字会严重损失。

#### 场景三：次正规数处理（下溢）
- **输入**：`[1e-38, 1e-38] + [1e-38, 1e-38]`（接近 FLOAT32 最小正规数）  
- **实测输出**：`[~2e-38, ~2e-38]`（次正规数或零，取决于 FTZ 设置）  
- **分析**：Ascend 910_93 默认保留次正规数，结果非零。但若启用 FTZ（Flush To Zero），则可能输出零。次正规数精度大幅降低，但避免了下溢到零。

#### 场景四：INT32 整数溢出
- **输入**：`[2^30, 2^30] + [2, 3]`，`alpha=1`  
- **实测输出**：`[-2147483648, -1073741824]`（按二进制补码截断）  
- **分析**：有符号整数溢出按低位截断，不会抛出异常。调用方需自行检查输入范围。

#### 场景五：混合类型精度（FP16 + FP32）
- **输入**：FP16 `[1.234, 2.345]` + FP32 `[0.123, 0.456]`  
- **实测输出**：`[1.357, 2.801]`（FP32 结果）  
- **误差**：相对误差 < 1e-3，符合 FP16 输入量化后的预期精度。

#### 场景六：alpha 非整数引入的累积误差
- **输入**：`[1.0, 2.0]` + `alpha=3.3333333f` × `[0.3, 0.6]`  
- **实测输出**：`[1.9999999, 3.9999998]`  
- **分析**：alpha 本身无法精确表示，导致乘积舍入后再加法，误差累加。在多次迭代中需关注。

## 五、反思与改进

### 测试盲区与局限性
- **V3 API 覆盖率极低**：仅测试了少数场景，未覆盖 V3 中的 Axpy 路径、类型提升路径、alpha≠1 时的 Mul+Add 通用路径。  
- **数据类型组合不全**：UINT8, INT16, COMPLEX32 等未测，导致 tiling 层大量分支未覆盖。  
- **非连续输入场景不足**：仅测试了基础视图，未覆盖高维非连续和与 Cast 组合的复杂情况。  
- **精度测试深度不够**：未系统测试 inf/NaN 传播、FTZ 行为等。

### 若有更多时间会如何扩展
1. **补充 V3 API 测试**：为 `aclnnAddV3` 添加 10+ 用例（不同 dtype、alpha 值，包括 Axpy 和不支持 Axpy 的类型），预计可提升 `aclnn_add_v3.cpp` 覆盖至 60%+。  
2. **增加 tiling 分支测试**：显式使用 `UINT8`, `INT8`, `COMPLEX32` 等数据类型，运行广播场景，触发 `add_tiling_arch35.cpp` 中未执行的 `DoOpTiling` 分支。  
3. **添加非连续 + Cast 测试**：构造非连续输入且需要类型转换的场景（如 FP16+FP32 混合类型但输入非连续）。  
4. **完善精度场景**：增加 inf/NaN 输入输出测试、次正规数 FTZ 行为验证、整数溢出回绕验证。

### 方法论层面的经验教训
- **Oracle 实现的陷阱**：FP16/BF16 的参考值必须通过位解码，不能直接使用 `uint16_t` 乘法，否则误差巨大。  
- **覆盖率工具的使用**：`gcov -b` 输出的分支覆盖率为加权平均值，需注意每个分支的独立执行情况。  
- **环境差异**：`ascend910_93` 真机与模拟器行为存在差异（如次正规数处理），测试应针对目标环境。

### 对 CANN 测试工具链的建议
- 提供更细粒度的覆盖率报告（如按函数展示未覆盖分支）。  
- 建议提供 `aclnnAddV3` 等 API 的示例测试代码，帮助开发者快速覆盖 V3 路径。  
- 增强 `asc_opc` 的调试信息，便于定位 kernel 编译失败的具体原因。
