# 算子测试报告


------

## 一、算子理解


Cumsum 的数学定义为前缀和。对一维情形，输出满足 `y[i] = sum_{j=0..i} x[j]`；对多维张量，则沿指定 `dim` 逐元素进行累积求和。题目同时要求关注 `aclnnCumsum` 与 `aclnnCumsumV2` 两类接口，其中 V2 额外支持 `exclusive` 与 `reverse` 两个布尔控制项，因此语义上不仅包含普通前缀和，还覆盖“排除当前元素的前缀和”和“从尾到头累积”的变体。

从实现结构看，Cumsum 位于 `math/cumsum/`，采用 `op_api -> op_host -> op_kernel` 三层架构。对测试而言，真正影响覆盖率的关键不只是 API 入参检查，还包括 host 侧 tiling 分支选择。当前评分重点覆盖 5 个文件：

| 文件 | 层级 | 主要职责 |
| --- | --- | --- |
| `op_api/aclnn_cumsum.cpp` | API | 参数校验、Cast/Contiguous、普通路径与 Cube 路径分流 |
| `op_api/cumsum.cpp` | API | AiCore / AiCPU 路由 |
| `op_host/arch35/cumsum_tiling.cpp` | Host | 按 dtype 分发到 float / int tiling |
| `op_host/arch35/cumsum_tiling_ascendc_arch35.cpp` | Host | 浮点类型 tiling 策略 |
| `op_host/arch35/cumsum_tiling_ascendc_int_arch35.cpp` | Host | 整数类型 tiling 策略 |

本算子的测试难点主要有三类：

- 累积误差。Cumsum 不是单次加法，而是误差会随序列长度传播与放大，因此长序列、非精确可表示小数、大小数混合输入都具有代表性。
- 路径分流较多。是否走 AiCore / AiCPU、普通 Cumsum / V2、float tiling / int tiling、以及 host 侧不同 `M/R/N` 切分策略，都会显著影响覆盖率。
- 边界语义较多。包括空 tensor、0 维标量、负 `dim`、`exclusive`、`reverse`、shape 不匹配、空指针、不支持 dtype 等。

## 二、测试策略与用例设计

建议包含：采用的测试方法思路、参照实现（Oracle）的选择、精度阈值的设定依据、用例的分类与分布、是否使用了辅助生成工具等。

本轮测试采用“语义正确性 + 覆盖率驱动 + 精度场景”三线并行的设计思路。具体来说，先在 CPU 侧实现独立 Oracle，保证每个成功用例都不是只打印输出，而是对照期望值进行自动判定；再结合源码结构补充能够命中不同 host tiling 分支的 shape / dtype / dim 组合；最后抽取一组有代表性的精度场景，在程序结尾统一汇总展示，便于后续报告分析与专家阅读。

### 2.1 Oracle 与结果判定

测试文件在 `math/cumsum/examples/test_aclnn_cumsum.cpp` 中实现了 CPU 参考版本 `CpuCumsum(...)`，支持：

- 普通 `Cumsum`
- `exclusive`
- `reverse`
- 负维度归一化
- 输入 dtype 与输出 dtype 的量化模拟

浮点类型采用容差判定：

| dtype | 判定方式 |
| --- | --- |
| `FLOAT32` / `DOUBLE` | `|actual - expected| <= atol + rtol * |expected|` |
| `FLOAT16` | 更宽松的浮点容差 |
| `BF16` | 使用更宽松容差，重点观察有效位损失 |
| 整数类型 | 精确匹配 |

当前测试中已经采用或对应题目要求的典型容差如下：

| dtype | 容差设置 |
| --- | --- |
| `FLOAT32` | `atol=1e-5, rtol=1e-5` |
| `FLOAT16` | `atol=1e-3, rtol=1e-3` |
| `BF16` | 视场景采用 `2e-2 ~ 3e-2` |
| `DOUBLE` | `1e-8` 量级 |
| 整数类型 | 精确匹配 |

### 2.2 用例组织方式

本轮用例分为两大类。

1. 成功路径用例  
   目标是校验数值正确性，同时命中不同实现分支。已覆盖：
   - `aclnnCumsum` 与 `aclnnCumsumV2`
   - `exclusive / reverse / exclusive+reverse`
   - `FLOAT / FLOAT16 / BF16 / DOUBLE / INT32 / INT64 / INT16 / INT8 / UINT8`
   - 0 维标量、空 tensor、负维度、不同轴位置
   - AiCPU 路径、AiCore 路径、Cube 支持路径
   - 多组专门为 host tiling 设计的 `M/R/N` 组合

2. 错误路径用例  
   目标是覆盖参数检查和异常返回。已覆盖：
   - `nullptr self`
   - `nullptr out`
   - 非法 dtype
   - shape 不一致
   - `dim` 越界
   - rank > 8
   - V2 下 `self/out` dtype 不一致

### 2.3 精度场景设计

除覆盖率驱动用例外，测试文件还加入了一组专门在结尾汇总的精度场景，当前包括：

| 场景 | 设计目的 |
| --- | --- |
| 长序列 `1.0` 累加（float32 / float16） | 观察误差随长度累积 |
| `0.1` 长序列累加 | 观察不可精确表示小数的传播误差 |
| 大小数混合 `[1e8, 1e-6, ...]` | 观察小量贡献被吞没 |
| 正负近抵消交替序列 | 观察 cancellation 对相对误差的放大 |
| `exclusive + reverse` | 验证 V2 组合语义及其精度表现 |
| BF16 小数累加 | 对比 BF16 与 float32 的有效位差异 |

### 2.4 输出格式设计

为避免运行时大量框架日志淹没测试结论，测试程序在所有 case 跑完后，统一输出两段摘要：

- `Final Test Results`：列出全部测试用例的 `Expected / Actual / Max error / [PASS]/[FAIL]`
- `Precision Test Summary`：只汇总精度重点场景，便于直接写入报告

这种组织方式比逐条翻运行日志更适合评审阅读，也便于后续多轮迭代时直接对比结果。

### 2.5 本轮执行结果概览

本轮测试分成两条线并行推进：

- 一条线继续提升覆盖率；
- 另一条线将精度测试缩减为“最小可复现探针”，优先确认最基础的 float32 路径是否正常。

当前已确认的最新现象如下：

- 覆盖率已提升到较高水平，尤其是 float host tiling 文件提升明显；
- 但即使将精度测试缩减为最简单的 `float32` 一维 `length=16` case，实际输出仍然是全 0；
- 因此当前问题已经可以明确归类为“功能异常优先”，而不是“大规模长序列下的误差累积问题”。

换言之，本轮报告的重点不再是“复杂精度场景的数学分析”，而是先证明一个更基础的事实：最小 float32 精度探针都未通过，这意味着后续所有复杂精度结论都应建立在先修复功能正确性的前提上。

### 3.4 结果解读

本轮覆盖率呈现出以下特点：

- `aclnn_cumsum.cpp` 行覆盖率已接近打满，说明 API 层的参数校验、空 tensor、普通路径、部分 Cube 条件都已经被覆盖。
- `cumsum_tiling.cpp` 行覆盖率为 100%，表明 dtype 分发入口已经被触达。
- 真正的主战场仍然是两个 host tiling 文件，尤其是 float tiling 文件。当前 `cumsum_tiling_ascendc_arch35.cpp` 已达到 `81.73%` 行覆盖和 `73.57%` 分支覆盖，说明覆盖率侧已经取得了明显进展。
- `cumsum.cpp` 覆盖率偏低，说明 AiCore / AiCPU 之外仍有部分未触发的分支，或某些分支只走到单侧未完成完整 branch coverage。

### 3.5 未覆盖部分的初步归因

结合源码和本轮结果，当前未覆盖区域主要集中在以下几类：

1. 浮点 tiling 的更深层 borrow 分支  
   例如 `NGreaterClRNotFullLoadBorrowR`、`RNGreaterClRNotFullLoadBorrowR` 及其 twoway 相关路径仍未完全打透。这类分支对 `M/R/N` 组合、`alignN`、UB 预算和借轴条件较敏感，往往需要更精细地构造 shape，而不是单纯放大张量规模。

2. schedule mode 相关分支  
   当前 `SetScheduleMode(1)` 对应路径尚未完整命中，说明虽然部分 core-ss 场景已触发，但还没有稳定进入所有需要设置 schedule mode 的 tiling key。

3. 整数 tiling 的 Group-R / 左轴分块路径  
   `cumsum_tiling_ascendc_int_arch35.cpp` 中与 `leftAxisLen / rightAxisLen / axis 位置` 强相关的分支还未完全覆盖，需要更有针对性的整数 shape 设计。

4. 平台或架构相关保底分支  
   如 `aclnn_cumsum.cpp` 中 `support for %s is not implemented` 这类分支，本轮环境下不会自然触发，属于平台依赖分支，不适合作为当前环境下的重点追求对象。

### 3.6 覆盖率与功能结果的关系

本轮覆盖率提升是真实的，但必须注意：覆盖率提升并不等于测试正确性已经达标。当前日志显示，大量失败 case 的 `Actual` 为全 0，这意味着：

- 一部分分支确实被执行到了，所以覆盖率上升；
- 但对应路径的功能结果仍不正确，因此不能将本轮覆盖率结果误解为“实现质量已经稳定”。

换句话说，本轮更像是“先把路径踩到了”，下一阶段则需要在已踩到这些路径的基础上，进一步修正测试或定位实现异常，使这些路径既被覆盖，又能给出正确输出。

## 四、精度分析

建议包含：误差度量方式与阈值、CPU 参考实现（Oracle）的选择依据、不同 dtype 下的精度表现；建议按**典型精度场景**（如下溢、上溢、临界值附近、整数溢出、dtype 对比、无法精确表示的小数等）分别展开，每个场景给出测试输入、实测输出、误差量化与成因分析；若存在精度不达标情形，给出根因分析。

### 4.1 误差度量方式

本测试使用 CPU 端独立实现的 `CpuCumsum(...)` 作为 Oracle。为尽可能接近设备侧实际行为，Oracle 在累加过程中显式模拟输入类型与输出类型的量化过程，而不是直接使用高精度数学和。这样做的优点是：

- 能更真实地反映 `FLOAT16/BF16` 的有效位损失；
- 能覆盖 `selfType != outType` 的 cast 场景；
- 能对 `exclusive`、`reverse`、负维度等语义进行统一校验。

误差判定方式如下：

- 浮点类型：`|actual - expected| <= atol + rtol * |expected|`
- 整数类型：要求精确相等

### 4.2 本轮精度测试场景

为了快速定位“Actual 全 0”问题，当前精度测试已从复杂长序列场景收敛为单个最小探针场景：

| 场景 | 输入特征 | 关注点 |
| --- | --- | --- |
| Basic Cumsum (float32, length=16) | `16` 个 `1.0` | 验证最基础的一维 float32 累积是否正常 |

### 4.3 本轮记录状态

本轮已经保存了可复核日志，且程序额外将精度摘要单独写入 `cumsum_precision_summary.log`。根据最新 `Precision Test Summary`，当前唯一保留的最小精度探针仍然失败，且失败形式依旧是 `Actual` 全 0：

| 场景 | 期望输出特征 | 实际输出特征 | 最大误差 | 结论 |
| --- | --- | --- | --- | --- |
| Basic Cumsum (float32, length=16) | 最终应得到 `[1.0, 2.0, ..., 16.0]` | 全 0 | `16.0` | FAIL |

这个结果非常关键，因为它把问题进一步收缩了：

- 现在失败的不是长序列、不是复杂 shape、也不是大小数混合；
- 失败的是最基础、最容易人工验证的一维 float32 前缀和；
- 因此可以确认当前主要矛盾与“误差累积数学性质”无关，而是更底层的功能正确性异常。

同时，本轮还额外做了日志输出优化：终端仍保留实时输出，精度摘要则单独保存到文件，便于报告引用。推荐保留如下工作方式：

```bash
bash build.sh --run_example cumsum eager cust --vendor_name=custom --soc=ascend910_93 --cov \
  > cumsum_round1.log 2>&1
```

### 4.4 预期分析框架

当基础功能恢复后，后续精度结论才适合重新扩展到以下角度：

1. 长序列误差累积  
   当序列足够长时，即使每一步舍入误差很小，最终偏差也会逐步扩大；float16 会比 float32 更明显。

2. 大小数混合的吞没现象  
   当累计和已达到 `1e8` 量级时，`1e-6` 这样的微小增量可能由于有效位不足而完全不再改变结果。

3. 不可精确表示小数的传播误差  
   如 `0.1` 在二进制中无法精确表示，因此长序列累加的理论值与机器结果之间会出现稳定偏差。

4. 抵消效应  
   正负交替且幅值接近时，绝对误差可能不大，但相对误差会被显著放大。

5. V2 模式的语义稳定性  
   `exclusive` 与 `reverse` 主要改变累加窗口，不改变误差来源，但会改变误差传播顺序，因此需要单独观察。

### 4.5 本轮初步诊断

结合全部测试结果，本轮可以给出一个更聚焦的判断：

- `double_aicpu_path_dim1` 与 `v2_double_aicpu_exclusive_reverse` 均通过，说明 CPU Oracle、基础比较逻辑、以及至少一部分 AiCPU 路径是工作的。
- `cube_support_float32` 通过，说明并非所有浮点路径都失效。
- 即使将精度测试缩减到最简单的 `float32 length=16` 场景，输出仍然全 0，进一步说明问题不是“复杂度过高”，而是某些普通 float 路径本身就异常。
- 多个整数路径通过，表明问题并不在“所有 dtype 全面失效”，而更可能集中在 float host / V2 相关路径。

因此，下一轮优化应优先回答两个问题：

1. 为什么这些路径的输出为全 0？  
2. 是算子实现问题、测试调用方式问题，还是某些路径下 `out` / workspace / launch 相关逻辑存在异常？

## 五、反思与改进

建议包含：测试盲区与局限性、若有更多时间会如何扩展、方法论层面的经验教训（例如 Oracle 实现、数据类型处理中的常见陷阱等）、对 CANN 测试工具链的建议。

### 5.1 当前局限

本轮虽然覆盖率已经进一步提升，但离最终目标 100% 仍有差距，说明当前 shape 设计仍然偏“经验驱动”，对部分复杂 borrow 分支的触发条件掌握还不够精确。特别是 float tiling 中多层 `M/R/N` 借轴组合，仅靠放大张量规模并不能稳定命中所有路径。

更重要的是，本轮暴露出的主问题已经从“覆盖率不足”升级为“最小 float32 探针都无法通过”。很多失败 case 不是误差略大，而是直接得到全 0 输出，这意味着当前测试工作不能只沿着“继续堆覆盖率”这一条线推进，还必须同步排查失败路径。

另外，运行时框架日志非常多，虽然程序末尾已经增加统一汇总，但日志仍可能与运行时析构信息交错，影响阅读体验。这是后续整理专家可读报告时需要持续优化的点。

### 5.2 下一轮改进方向

下一轮建议优先做三件事：

1. 对未覆盖分支做更细粒度反推  
   直接结合 `.gcov` 未命中行与源码条件，针对性构造能进入指定 tiling key 的 shape，而不是继续粗放扩大 case 数量。

2. 优先定位“最小 float32 case 仍输出全 0”的失败模式  
   下一轮不应只看覆盖率数字，而应继续使用“小探针”思路，把失败 case 按路径聚类，重点区分：
   - 普通 float32 一维路径
   - V2 浮点路径
   - float host 多维路径
   - AiCPU / Cube 对照路径

3. 将运行结果落盘  
   统一保存每轮 `run_example` 输出，方便从日志末尾稳定抽取精度摘要、总通过数与失败 case。

4. 区分“快速回归集”和“冲覆盖率集”  
   当前部分 case 已经比较重，虽然比前一版有所缩减，但仍不适合高频手工迭代。后续可将用例分为：
   - 日常快速验证集
   - 最终提交前的重覆盖集

### 5.3 方法论上的经验

- 对 Cumsum 这类“语义简单但实现分支复杂”的算子，覆盖率优化的重点不在数学定义本身，而在 host tiling 条件推导。
- 设计 Oracle 时，不能只用高精度 CPU 累加后直接比较；必须考虑输入输出 dtype 的量化行为，否则容易把正常的低精度舍入误判为错误。
- 从本轮经验看，测试报告必须区分“功能错误”和“精度误差”。当 `Actual` 全 0 时，应该首先归类为功能异常，而不是仓促写成“数值精度退化”。
- 对评审友好这一点非常重要。相比只堆运行日志，更有效的做法是在程序结尾统一输出结构化摘要，再在报告中以段落解释思路、以表格呈现结果、以条目列出未覆盖原因。

### 5.4 对工具链的建议

- 若覆盖率脚本能够自动附带“未覆盖行 TopN”摘要，将显著提高定向补 case 的效率。
- 若测试框架支持把最终 `PASS/FAIL` 摘要单独输出到文件，将更利于比赛场景下的多轮报告迭代。
- 当前 `gcov` 会提示某些外部头文件无法打开，但不影响目标文件统计。若能在脚本中统一过滤此类噪声提示，结果会更清晰。
