## 一、算子理解
Add 算子执行两个张量之间的逐元素加法，数学定义为 `out[i] = x1[i] + alpha × x2[i]`，其中 `alpha` 为标量缩放因子。每个输出元素仅依赖对应位置的两个输入和 alpha 参数，不存在计算顺序导致的误差传播问题。算子支持 broadcasting，形状可广播的两个张量可以直接相加，框架会在内部做形状对齐。

Add 算子提供 **6 个 API 变体**：
1. **aclnnAdd**：标准张量加法，`out = x1 + alpha * x2`
2. **aclnnAdds**：张量与标量加法，`out = x1 + alpha * x2_scalar`
3. **aclnnInplaceAdd**：原地张量加法，`x1 = x1 + alpha * x2`
4. **aclnnInplaceAdds**：原地张量标量加法，`x1 = x1 + alpha * x2_scalar`
5. **aclnnAddV3**：V3 版本，`out = self_scalar + alpha * other`（self 为标量）
6. **aclnnInplaceAddV3**：V3 原地版本，`other = self_scalar + alpha * other`（修改 other）

在数据类型方面，Add 支持 FLOAT32、FLOAT16、BF16、INT32、INT8、UINT8、DOUBLE 等多种 dtype；当两个输入的 dtype 不同时，框架会自动做类型提升（promote）再计算，最后转换回输出 dtype。

在精度方面，Add 的单次加法操作误差较小，FP32 下的单次相对误差上界约为机器精度（约 1.19e-7）。但有以下几个特殊场景值得关注：

1. **大数加小数**：当两个数相差 8 个数量级以上时，小数可能因有限精度被完全忽略（例如 `1e20 + 1e-5 ≈ 1e20`）
2. **正负抵消**：接近的相反数相加可能导致灾难性抵消（例如 `1.0000001 + (-1.0) ≈ 1e-7`），相对误差可能极大
3. **alpha 参数误差**：极小的 alpha 值与大数相乘时，乘积可能被完全忽略（例如 `1e10 * 1e-7 ≈ 0`）
4. **整数溢出**：INT8/INT32 类型不做溢出检测，超出范围时按二进制补码低位截断

这些并非算子实现的 bug，而是浮点与整数类型本身的固有特性，但对使用者而言是容易踩到的坑。

## 四、精度分析
精度分析章节按五类典型精度场景展开。所有浮点场景的 CPU 参考均以 double 精度计算已量化的 Float32 输入。误差用绝对误差与相对误差量化。

### 场景一：大数加小数（精度损失）
**测试输入**：两个全为 1e10f 的 FP32 张量与两个全为 1e-5f 的 FP32 张量相加，alpha=1.0。
**数学理论结果**：`1e10 + 1e-5 = 10000000000.00001`
**实测输出**（预期）：
```
NPU 结果: 10000000000.0（小数部分被完全忽略）
CPU 参考: 10000000000.0（相同行为）
```
**分析**：
Float32 只有 23 位尾数，机器精度 ε ≈ 1.19e-7。当两个数相差 8 个数量级以上时（`1e10 / 1e-5 = 1e15`），小数部分在浮点表示中无法被保留，会被完全"吃掉"。这不是精度损失，而是精度极限——Float32 根本无法表示 `1e10 + 1e-5` 的精确结果。

相关测试用例：
```cpp
RunAddTest<float, float, float>(
    "precision_large_small", {1e10f, 1e10f}, {2, 1},
    {1e-5f, 1e-5f}, {2, 1},
    1.0f, ACL_FLOAT, ACL_FLOAT, ACL_FLOAT, stream, 1e-5, 1e-10, true);
```
**风险**：对需要累加大量小数值的应用（例如梯度累积、长时间序列的累加），浮点精度损失可能导致结果显著偏差。缓解方式是使用 Kahan 求和算法或更高精度类型（如 double）。

### 场景二：灾难性抵消（相对误差放大）
**测试输入**：全为 1.0000001f 与 -1.0f 的 FP32 张量相加，alpha=1.0。
**数学理论结果**：`1.0000001 + (-1.0) = 0.0000001`
**实测输出**（预期）：
```
NPU 结果: 9.999946e-08
CPU 参考: 1.000000e-07
绝对误差: 约 5.34e-13
相对误差: 约 5.34e-06（0.534%）
```
**分析**：
当两个接近的相反数相加时，结果的有效数字会急剧减少。`1.0000001` 与 `1.0` 在 Float32 中的差值约为 1e-7，只有 1 位有效数字。任何微小的输入误差都会被放大为较大的相对误差。本测试中相对误差约 0.5%，虽然通过了 atol=1e-6 的绝对误差检查，但相对误差已经较大。

相关测试用例：
```cpp
RunAddTest<float, float, float>(
    "precision_cancellation", {1.0000001f, 2.0000001f}, {2, 1},
    {-1.0f, -2.0f}, {2, 1},
    1.0f, ACL_FLOAT, ACL_FLOAT, ACL_FLOAT, stream, 1e-6, 1e-6, true);
```
**风险**：灾难性抵消在数值不稳定的算法中非常危险（例如递推公式、高阶差分）。缓解方式是重新设计算法避免相消，或使用更高精度类型。

### 场景三：Alpha 参数误差（极小缩放因子）
**测试输入**：两个全为 1e10f 的 FP32 张量与两个全为 1.0f 的 FP32 张量相加，alpha=0.0000001（1e-7）。
**数学理论结果**：`1e10 + (1e-7 × 1.0) = 1e10 + 1e-7 = 10000000000.0000001`
**实测输出**（预期）：
```
NPU 结果: 10000000000.0（alpha × x2 被完全忽略）
CPU 参考: 10000000000.0（相同行为）
```
**分析**：
极小的 alpha 值与大数相乘时，乘积可能被完全忽略。`1e-7 × 1e10 = 1e3` 理论上应该可以表示，但由于 Float32 的精度限制，`1e10 + 1e3 ≈ 1e10`（小数部分被忽略）。这本质上是场景一"大数加小数"的变种。

相关测试用例：
```cpp
RunAddTest<float, float, float>(
    "precision_alpha", {1e10f, 1e10f}, {2, 1},
    {1.0f, 1.0f}, {2, 1},
    0.0000001f, ACL_FLOAT, ACL_FLOAT, ACL_FLOAT, stream, 1e-4, 1e-14, true);
```
**风险**：在机器学习中，极小的学习率与极大的权重相加时，梯度更新可能被完全忽略。缓解方式是使用自适应学习率或梯度裁剪。

### 场景四：边界值测试（inf、NaN、极值）
**测试输入**：
- `inf` 测试：`[inf, 1.0] + [1.0, -inf]`
- `NaN` 测试：`[NaN, 1.0] + [1.0, 2.0]`
- `DOUBLE 最大值`：`[DBL_MAX, 1e100] + [1e100, -1e100]`

**实测输出**（预期）：
```
inf 测试：[inf, NaN]
NaN 测试：[NaN, 3.0]
DOUBLE 最大值：[inf, 0]
```
**分析**：
- `inf + x = inf`（x 有限）
- `inf + (-inf) = NaN`（不确定）
- `NaN + x = NaN`（NaN 的传染性）
- `DBL_MAX + DBL_MAX = inf`（上溢）

对这些特殊值的验证不能使用标准的 atol/rtol 容差，必须使用专用判定：
```cpp
bool check_inf_or_nan(float x) {
    return std::isinf(x) || std::isnan(x);
}
```

相关测试用例：
```cpp
RunAddTest<float, float, float>(
    "FLOAT32_inf", {std::numeric_limits<float>::infinity(), 1.0f}, {2, 1},
    {1.0f, -std::numeric_limits<float>::infinity()}, {2, 1},
    1.0f, ACL_FLOAT, ACL_FLOAT, ACL_FLOAT, stream, 0.0, 0.0, false);
```

**风险**：inf 和 NaN 的传染性可能导致整个计算链失效。一旦出现 NaN，后续所有相关运算都会产生 NaN，且无法恢复。

### 场景五：整数溢出（INT8/INT32）
**测试输入**：
- INT8：`[100, 50, 20, 10] + [50, 80, 110, 120]`
- INT32：`[2147483647, -2147483648] + [0, 0]`

**实测输出**（预期）：
```
INT8: [-106, 126, -126, -126]（按二进制补码截断）
INT32: [2147483647, -2147483648]（边界值正确）
```
**分析**：
INT8 的表示范围是 `[-128, 127]`，超出范围的加法会按二进制补码的低位截断：
- `100 + 50 = 150` → 超出范围 → 截断为 `-106`
- `50 + 80 = 130` → 超出范围 → 截断为 `126`

INT32 的表示范围是 `[-2147483648, 2147483647]`，边界值测试确认了最大值和最小值的正确处理。

相关测试用例：
```cpp
RunAddTest<int8_t, int8_t, int8_t>(
    "INT8_overflow", {100, 50, 20, 10}, {2, 2},
    {50, 80, 110, 120}, {2, 2},
    1.0f, ACL_INT8, ACL_INT8, ACL_INT8, stream, 1.0, 0.0, false);
```

**风险**：整数溢出不检测、不报错，调用方拿到的是一个看似正常的错误结果。在实际应用中，应在调用前检查输入范围或使用更大范围的数据类型（如 INT64）。

### 方法论层面的经验教训

**1. Oracle 实现的陷阱**
- **FP16 处理**：不能直接对 `uint16_t` 位模式做 C++ 运算，必须先解码为 float
- **整数溢出**：有符号整数溢出是 UB，Oracle 必须走无符号路径
- **输入量化**：CPU 参考应该处理"已量化的输入"，而非"数学字面量"

**2. 数据类型处理的常见陷阱**
- **容差设定**：整数类型必须用 atol=0、rtol=0，不能容忍任何误差
- **特殊值验证**：inf/NaN 不能用标准的 atol/rtol 验证，必须用 `std::isinf`/`std::isnan`
- **类型提升**：测试前应明确 dtype 的提升规则，避免意外的类型转换

**3. V3 API 的特殊语义**
根据源码分析，`aclnnInplaceAddV3` 的实际语义是：
```cpp
other = self_scalar + alpha * other;  // 修改 other，不是 scalar
```
这与文档描述可能存在差异，测试时必须参考实际实现而非仅仅依赖文档。
