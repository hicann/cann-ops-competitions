# Cumsum 算子测试报告

> 测试环境：Ascend 910 系列环境，SOC 参数使用 `ascend910_93`，CANN 工具链版本从覆盖率路径可见为 `cann-9.0.0-beta.2`。本报告基于提交的 `test_aclnn_cumsum.cpp` 测试源文件与 `gcov -b -c` 覆盖率输出整理。不同硬件型号、CANN 版本、编译选项和浮点处理模式下，极端精度场景的实测误差可能存在差异。

------

## 一、算子理解

Cumsum 算子用于沿指定维度对输入张量执行累积求和。对于一维输入，其基本数学定义为：

```text
y[i] = x[0] + x[1] + ... + x[i]
```

对于多维张量，Cumsum 并不是对整个张量展平后统一求前缀和，而是沿参数 `dim` 指定的维度分别对每条 slice 做前缀累加。假设输入张量为 `x`，输出为 `y`，在第 `dim` 个维度上，普通模式下可以表示为：

```text
y[..., i, ...] = sum_{j=0}^{i} x[..., j, ...]
```

该算子对外主要包含两个 API 入口：`aclnnCumsum(self, dim, dtype, out)` 与 `aclnnCumsumV2(self, dim, exclusive, reverse, out)`。前者实现标准累积求和，后者支持 `exclusive` 与 `reverse` 两个控制参数。其中 `exclusive=true` 时当前位置输出不包含当前输入元素，第一项通常为 0；`reverse=true` 时累加方向由后向前进行；二者同时为 true 时表示从尾部开始做不含当前元素的反向前缀和。

Cumsum 的主要输入约束包括：输入、输出 tensor 形状需要匹配；`dim` 需要落在合法维度范围内，负维度需要被转换为对应的正维度；`dtype` 或输出 dtype 需要与算子支持的类型组合匹配。本次测试覆盖了 `FLOAT32`、`FLOAT16`、`BF16`、`INT32`、`INT64`、`INT8 -> INT32` 等类型。与 Mul、Add 等逐元素算子不同，Cumsum 的每个输出元素依赖前面多个输入元素，误差会随着累加长度传播和放大，因此长序列、小数累加、正负抵消、大小数混合以及低精度 dtype 是重点关注场景。

## 二、测试策略与用例设计

本次在 `test_aclnn_cumsum.cpp` 中构造了 71 个端到端测试用例，测试流程遵循“CPU 参考实现计算期望值 → 创建 ACL Tensor → 调用 Cumsum API → 拷回 NPU 输出 → 与期望值比较 → 输出 PASS/FAIL”的方式。测试代码保留官方 example 的初始化、stream 创建、device 内存申请和 tensor 创建流程，同时补充了多类型、多维度、多 shape、多 API 变体的结果验证逻辑。

**Oracle 设计。** 浮点类型的 CPU 参考实现使用 `double` 作为累加中间类型，避免 CPU 侧参考值本身过早发生明显舍入。对于多维张量，测试代码没有简单地对线性内存做一维前缀和，而是实现了 `LinearToCoord`、`CoordToLinear` 等索引转换函数，沿指定 `dim` 找到每一条 slice 独立累加，从而与 Cumsum 的真实语义保持一致。对于 `dim < 0` 的场景，CPU 参考中先将负维度转换成正维度，再进行计算。

**低精度类型处理。** FP16 与 BF16 不能直接用 `uint16_t` 位模式参与 C++ 算术运算，否则会把浮点编码当作整数处理，得到错误参考值。因此测试代码分别实现了 `FloatToFp16`、`Fp16ToFloat`、`FloatToBf16`、`Bf16ToFloat` 辅助函数。FP16/BF16 用例先将输入浮点值编码成相应低精度格式，再解码回 float 作为 CPU 参考输入，保证 CPU 参考和 NPU 实际输入处于同一量化基准上。

**容差策略。** FLOAT32 主要使用 `atol=1e-5, rtol=1e-5`，在长序列或大数场景适当放宽到 `1e-4`、`1e-3` 或更高；FLOAT16 使用 `1e-2` 到 `5.0/0.05` 级别的容差以兼容半精度累加误差；BF16 使用 `5e-2` 级别容差；整数类型采用精确匹配。对于 INT32 溢出场景，测试代码没有简单地用有符号溢出作为参考，而是在期望值超出 INT32 表示范围时用无符号截断方式构造比较值，从而避免 C++ 有符号溢出未定义行为对 Oracle 的影响。

本次用例主要分为六类：

| 类别 | 覆盖内容 | 代表用例 |
| --- | --- | --- |
| 基础 dtype | FP32、FP16、BF16、INT32、INT64、INT8 输入转 INT32 输出 | `FP32 1D dim=0 [5]`、`BF16 1D dim=0 [4]`、`INT8->INT32 1D dim=0 [8]` |
| 多维 shape 与 dim | 1D、2D、3D、4D、5D，覆盖 `dim=0/1/2/3/4` 和 `dim=-1` | `FP32 3D [2,3,2] dim=2`、`FP32 5D [2,2,2,2,2] dim=4` |
| 序列长度 | 短序列、中等序列、长序列、二维大张量 | `FP32 len=500`、`FP32 len=10000 all 1.0`、`FP32 2D [100,100] dim=1` |
| 数值特征 | 全正、全负、正负混合、全零、含零、单元素、大数、小数 | `FP32 mixed pos/neg`、`FP32 large values 1e30`、`Precision: 10000x0.1 FP32` |
| API 变体 | Cumsum 与 CumsumV2，覆盖 exclusive、reverse 及二者组合 | `V2 FP32 exclusive 1D`、`V2 FP32 excl+rev 1D`、`Precision: V2 excl+rev len=5000` |
| 精度风险 | 误差累积、大小数混合、正负抵消、低精度对比、整数溢出 | `Precision: large/small alternating`、`Precision: FP16 100x1.5`、`Precision: INT32 overflow` |

整体设计目标不是只验证少数正常输入，而是通过 dtype、shape、dim、序列长度和 V2 标志位的组合，尽可能触发 op_api 层的参数处理、设备路由以及 op_host tiling 层的不同分支。

## 四、精度分析

Cumsum 的精度风险来自“累积”这一计算结构。对于普通逐元素算子，单个输出通常只经历一次或少数几次浮点操作；而 Cumsum 第 `i` 个输出需要经历 `i+1` 次输入贡献的累计，因此舍入误差会沿序列向后传播。测试代码采用如下误差判定方式：

```text
|actual - expected| <= atol + rtol * |expected|
```

其中浮点 expected 由 CPU 端 double 精度参考实现给出，actual 来自 NPU 输出。整数类型使用精确匹配，溢出场景单独按截断语义处理。

### 场景一：长序列累加的误差增长

**测试输入**：`Precision: 10000x1.0 FP32`，输入为 10000 个 `1.0f`，沿一维做 Cumsum。

**理论期望**：第 `i` 个输出为 `i+1`，最后一个输出理论值为 `10000.0`。

**分析**：对于 `1.0f` 这类可被二进制浮点精确表示的小整数累加，在结果未超过 FP32 精确整数表示范围时，理论上误差很小。但该用例仍然有意义，因为它覆盖了长序列下的 tiling、循环与累积主路径，可以检查长序列下是否存在分块边界错误、前缀状态传递错误或尾块处理错误。测试中对该类长序列设置了相对宽松的容差，是为了兼容不同硬件/实现可能采用的分块累加策略；只要最终误差在容差范围内，就说明主计算路径满足精度要求。

### 场景二：无法精确表示的小数累加

**测试输入**：`Precision: 10000x0.1 FP32`，输入为 10000 个 `0.1f`。

**理论期望**：数学上最后一个输出接近 `1000.0`。

**分析**：十进制小数 `0.1` 不能被二进制浮点精确表示，存入 FP32 时已经变成一个近似值。Cumsum 会把这种输入量化误差和每一步加法舍入误差不断累积，因此序列越长，末尾输出越容易出现可观测偏差。该现象不是 Cumsum 算子特有 bug，而是二进制浮点表示与累积求和共同导致的数值现象。测试中使用 double 参考值对“已量化后的 float 输入”累加，避免把数学字面量 `0.1` 的理想值误当成 NPU 输入的真实基准。

### 场景三：大小数混合导致小量贡献被吞没

**测试输入**：`Precision: large/small alternating`，构造类似 `[1e8, 1e-3, 1e8, 1e-3, ...]` 的大小数交替序列。

**理论现象**：当累加和已经达到 `1e8` 量级时，继续加入 `1e-3` 这样的小数，其贡献可能低于当前浮点间隔，无法改变 FP32 表示值。

**分析**：FP32 的有效位数有限，数值越大，相邻可表示浮点数之间的间隔也越大。在 `1e8` 量级，`1e-3` 的贡献远小于当前量级下的分辨率，因此小数项在累加中可能被舍入掉。Cumsum 在此类输入下的误差不是随机噪声，而是具有方向性的“小量丢失”。该用例主要验证算子面对非均匀量级输入时的结果是否与浮点语义一致，同时提醒使用者：如果业务场景需要保留小量贡献，可能需要采用更高精度累加、重排求和或补偿求和策略。

### 场景四：正负交替抵消

**测试输入**：`Precision: pos/neg alternating cancellation`，构造正负交替序列，例如大正数与接近相反数反复出现。

**理论现象**：数学上正负项会发生抵消，但在浮点中，两个接近的大数相减后可能暴露前面累积的舍入误差，造成相对误差放大。

**分析**：正负抵消场景的绝对误差未必非常大，但当真实结果接近 0 时，相对误差会显得很高。Cumsum 的中间状态会影响后续所有输出，因此抵消发生的位置越靠前，对后续输出的影响越长。测试中保留绝对误差与相对误差混合容差，是因为仅使用相对误差会在 expected 接近 0 时过于苛刻，而仅使用绝对误差又不能反映大值输出的相对偏差。

### 场景五：FP32、FP16 与 BF16 的误差差异

**测试输入**：`Precision: FP32 100x1.5`、`Precision: FP16 100x1.5`，以及 BF16 基础与 V2 用例。

**理论现象**：FP16 和 BF16 的有效位数少于 FP32。FP16 具有较小的动态范围和较少尾数位，BF16 动态范围接近 FP32 但尾数位更少，因此二者在累积求和时更容易出现舍入误差。

**分析**：本次测试对 FP16/BF16 的 Oracle 做了专门编码/解码处理，使参考值基于实际低精度输入，而不是理想 float 字面量。FP16 用例使用更宽的容差，原因是每一步累加都可能发生更粗粒度舍入，长序列下误差增长明显快于 FP32。BF16 虽然能表示更大的数值范围，但尾数精度较低，适合对动态范围敏感但对尾数精度要求不极端的场景；若业务需要精确累计小数，BF16/FP16 均可能不如 FP32 稳定。

### 场景六：整数累加与溢出

**测试输入**：`Precision: INT32 overflow`，构造接近或超过 INT32 表示范围的累加序列。

**理论现象**：整数类型没有舍入误差，但存在溢出风险。当累加结果超过 `INT32_MAX` 或低于 `INT32_MIN` 时，输出会按照底层整数表示发生截断或回绕，结果可能与数学整数求和不同。

**分析**：测试代码用 INT64 保存 CPU 参考累加值，以便先得到数学意义上的真实和；当 expected 超出 INT32 范围时，再按无符号截断方式转换成 INT32 进行比较。这种写法避免了 C++ 有符号整数溢出的未定义行为，也更贴近底层二进制结果验证。该场景说明，整数 Cumsum 的风险不在舍入，而在范围；实际使用中若累加长度较长或输入值较大，应优先考虑更宽的输出 dtype。

### 场景七：CumsumV2 的 exclusive 与 reverse 精度特性

**测试输入**：`V2 FP32 exclusive 1D`、`V2 FP32 reverse=true 1D`、`V2 FP32 excl+rev 1D`、`Precision: V2 excl+rev len=5000` 等。

**理论现象**：`exclusive` 改变的是当前位置是否包含当前输入，`reverse` 改变的是累加方向。二者不会改变浮点加法的基本误差机制，但会改变误差传播方向和每个位置对应的累加项集合。

**分析**：普通 Cumsum 中，越靠后的输出通常经历越多次累加；reverse 模式下，误差累积方向反过来，越靠前的位置可能经历更多次累加；exclusive 模式会使输出整体相对普通模式错开一个位置。测试中分别覆盖四种布尔组合，能够验证 V2 API 的语义正确性，并检查反向扫描、首尾边界、exclusive 初值为 0 等容易出错的位置。

## 五、反思与改进

本次测试的主要优点是覆盖面较广：一方面，测试不只覆盖了 FP32 基础路径，还覆盖了 FP16、BF16、INT32、INT64、INT8 转 INT32 等 dtype；另一方面，测试同时覆盖了一维到五维 shape、正维度和负维度、短序列和长序列、普通 Cumsum 和 CumsumV2 的 exclusive/reverse 组合。因此从覆盖率结果看，API 主干路径和 host tiling 主流程均已被有效触发，综合行覆盖率达到约 67.64%，综合分支覆盖率达到约 45.51%。

本次测试的不足主要集中在异常路径和更极端的 tiling 分支。当前用例以“能够稳定运行并通过”为优先目标，较少主动构造非法输入，例如 nullptr、非法 dim、输入输出 shape 不一致、不支持 dtype、空 tensor、极端 rank 或极端 shape 等。由于这些异常路径通常包含大量 `if-else` 分支，因此会明显影响分支覆盖率。若后续有更多时间，可以在保证评测流程不被中断的前提下，单独设计预期失败用例，并验证 API 是否返回合理错误码，从而提升 `aclnn_cumsum.cpp` 和 `cumsum.cpp` 的分支覆盖。

第二个改进方向是进一步针对 tiling 边界设计 shape。当前测试已经包含 `[100,100]`、`[256,16]`、`[16,256]`、长度 4096/5000/10000 等输入，但 tiling 文件仍有较多未覆盖代码。后续可以结合 `.gcov` 行级结果，反推未覆盖分支对应的阈值条件，补充刚好落在 tiling 边界两侧的 shape，例如维度长度为 1、2、31、32、64、128、255、256、1024、4096 及其附近值，以触发不同分块策略、尾块路径和特殊优化路径。

第三个经验是 Oracle 的正确性必须单独重视。Cumsum 看似简单，但一旦涉及 FP16/BF16 位模式、多维 dim、reverse/exclusive 组合以及整数溢出，CPU 参考实现很容易写错。特别是低精度类型，如果直接把 `uint16_t` 位模式当整数或普通 float 运算，测试会产生虚假失败；整数溢出如果直接用 C++ 有符号类型计算，也可能引入未定义行为。因此，本次测试专门实现了低精度编解码、多维索引映射和 INT64 中间累加，是提高测试可信度的关键。

最后，对 CANN 测试工具链的建议是：在比赛或日常测试中，最好同时提供文件级覆盖率汇总和评分文件过滤脚本。`gcov` 默认会输出大量 C++ 标准库、CANN 头文件和内部依赖文件，容易干扰参赛者判断真正评分文件的覆盖情况。如果官方脚本能直接输出 5 个评分文件的行覆盖、分支覆盖、调用覆盖和综合加权结果，将更有利于快速定位测试盲区并提高迭代效率。
