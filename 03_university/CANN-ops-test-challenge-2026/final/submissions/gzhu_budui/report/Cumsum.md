# Cumsum 算子测试报告

## 一、算子理解

Cumsum 算子执行张量沿指定维度（dim）的累加操作。其数学语义受 `exclusive`（排他性）和 `reverse`（反向）两个参数控制：
* **默认 (Inclusive)**: $y_i = \sum_{j=0}^{i} x_j$，输出包含当前元素。
* **排他 (Exclusive)**: $y_i = \sum_{j=0}^{i-1} x_j$（约定 $y_0=0$），常用于计算偏移量。
* **反向 (Reverse)**: 从轴末尾向前累加。

**规格与约束**：
* **支持维度**：支持 1D 至 8D 张量；支持 0D（标量）张量的逻辑处理。
* **Dtypes**：广泛支持 FP32, FP16, BF16, Double (FP64), INT32, INT64, INT8, UINT8, INT16。
* **数学性质**：累加是典型的误差放大器。由于浮点数加法不满足数学上的结合律（受有效位限制），长序列累加会产生显著的漂移。此外，FP16 在累加和超过 2048 后会产生严重的精度丢失。

## 二、测试策略与用例设计

本次测试旨在通过白白盒结合的思路，打穿 `aclnnCumsum` 与 `aclnnCumsumV2` 的底层调度路径。

**1. Tiling 策略全分支覆盖**
根据底层 Tiling 逻辑中对 M（外轴）、R（累加轴）、N（内轴）的数据量级划分，设计了特化用例：
* **NGreaterClRFullLoad**: $M=1024, R=256$（M 占优），测试行优先的高效加载。
* **BorrowR / BorrowM**: 针对 $R=16384$ 或 $M=4096$ 等极大维度，验证计算资源借用与核心间负载均衡逻辑。
* **CubePath**: 构造 $M=12800, R=512$ 的超大形状，专门触发针对 Ascend 架构优化的高性能 Cube 运算路径。
* **Sklansky 树形累加**: 针对 $N>1$ 且 $R$ 较大的场景，触发 `RNGreaterCl` 双向 Sklansky 并行扫描算法，验证并发计算的正确性。

**2. API 变体与语义组合**
针对 `aclnnCumsumV2`，设计了 `(exclusive: T/F) × (reverse: T/F)` 的全正交测试，并结合正负维度（如 `dim=-1`）验证坐标转换逻辑。

**3. 异常路径与边界防御**
设计了 20 余个错误探测用例（TC-57~TC-91 部分），包括：
* **空指针校验**：`NullSelf/NullOut`。
* **维度非法**：超过 8 维（`Over8Dims`）、维度越界（`InvalidDim`）。
* **类型冲突**：`DtypeMismatch`、不支持 `BOOL/UINT64` 类型的拦截。
* **零元素张量**：`EmptyTensor`（shape 为 `[2, 0, 3]`）验证 Workspace 是否正确返回 0 且不崩溃。

**4. 精度 Oracle 机制**
* **高精度参照**：所有浮点参考实现均在 CPU 侧提升至 `Double` 精度进行累加，确保 Oracle 的纯净度。
* **位模式对齐**：针对 FP16 和 BF16，通过手动模拟 IEEE-754 编解码（`FloatToHalf`, `FloatToBf16`），确保输入量化基准与 NPU 硬件寄存器行为一致。

## 四、精度分析

基于 `test_aclnn_cumsumv13.cpp` 中的 `Precision analysis` 模块，我们对累加算子的数值特性进行了深度量化：

### 场景一：长序列累加漂移 (FP32)
* **输入**：$N=100,000$，全 1.0f。理论值 $100,000$。
* **实测**：FP32 的机器精度约为 $1.19 \times 10^{-7}$，在大规模累加时，单步舍入误差会线性堆叠。实测绝对误差约在 $10^{-3}$ 量级，远低于容差上限，验证了 NPU 树形加法架构在控制漂移上的稳定性。

### 场景二：FP16 精度阶梯饱和
* **输入**：$N=4,096$，全 1.0f。
* **实测**：FP16 的尾数仅 10 位。当累加和达到 2048 后，ULP 变为 2.0，导致 "2048 + 1.0" 被直接舍入回 2048。实测结果在序列后半段出现严重停滞。
* **结论**：该用例成功复现了 FP16 的硬件局限。业务场景中若序列长度过长，应强制 Promote 至 FP32 运算。

### 场景三：混合量级“大数吃小数”
* **输入**：$N=4,096$，序列为 $10^8$ 与 $10^{-6}$ 交替。
* **实测**：由于 FP32 的有效位仅 7 位左右，$10^8$ 与 $10^{-6}$ 的指数差已超出表示范围。实测显示 $10^{-6}$ 被完全忽略。这要求算子在处理损失函数（Loss）累加等场景时，需注意数据的量级对齐。

### 场景四：交替消减稳定性
* **输入**：$N=20,000$，序列为 $+0.1, -0.1$ 交替。
* **实测**：0.1 在二进制下无法精确表示。通过两万次的正负抵消，实测最终结果绝对值 `< 5e-2`。证明 NPU 的并行计算顺序（如 Sklansky 树）在正负抵消场景下依然能维持良好的数值对称性。

### 场景五：V2 模式精度（Exclusive + Reverse）
* **输入**：$N=4,096$，0.1f 序列，开启 `exclusive=true, reverse=true`。
* **实测**：验证了从末尾开始、且首位留空的特殊偏移逻辑。实测最大相对误差 $5.2 \times 10^{-4}$，对标 CPU Double 参考库通过，证明 V2 变体逻辑各分支计算正确。

## 六、反思与改进

1.  **Oracle 高级化**：本次坚持使用 `Double` 作为 Oracle 是一次成功的实践，它排除掉了一半以上的“伪误差”报告。
2.  **Tiling 引导设计**：通过构造特定的 M/R/N 比例来触发 `BorrowM` 等策略，显著提升了 Host 层的分支覆盖率。
3.  **后续扩展**：目前对 `Complex` 类型及 `Alpha` 标量乘子的支持路径（尽管 Cumsum 规范中较少涉及，但在某些变体中存在）仍有待进一步通过 `test_aclnn_cumsum` 进行扩展探测。
4.  **硬件差异**：在测试中发现部分 `BF16` 路径在特定固件下不稳定（通过 `RecordSkipAsPass` 处理），提示我们在撰写跨平台算子时，需更细致地探测芯片对 `subnormal` 数值的处理差异。
