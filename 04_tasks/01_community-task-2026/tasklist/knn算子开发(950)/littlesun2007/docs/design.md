# 需求背景

## 需求来源

CANN 训练营 KNN 算子开发（950）：在 PyTorch 层提供 torch_cluster 风格
的 `knn` / `knn_graph`，支持 FP16/FP32、欧氏和余弦距离，用于图构建。
性能表含 32 个 `(N,F,k)` 组合、两种 dtype，全部达到标杆的 0.45 倍。

## 背景与现状

上游 ops-gnn 基点 `2a6922c46accd89a94aa464a36558c0efddeffc6` 没有本实现。
复用仓库已存在的 Ascend C/pybind 构建路径，新增 KNN 目录和 Python 接口。
社区 DrivingSDK 的候选分块/排序、PyTorch3D 的查询缓存与小 K 专用化、
Faiss/cuVS 的流式 Top-K 作为结构参考，不直接复制 CUDA 或 A2 硬件参数。
当前采用查询缓存加流式选择；尚未引入候选分块和跨线程合并。

# 需求分析

## 功能拆解

- 输入同设备 FP16/FP32 `x[N,F]`、`y[M,F]`，1D 自动转列向量。
- sorted int64 batch 经 bucketize 转为指针；仅在同 batch 搜索。
- 输出 int64 `[2,M*k]`：查询索引和源点索引。空输入输出 `[2,0]`。
- cosine 在 NPU 支持，`num_workers` 参数保留但忽略。
- 图接口复现 `k+1` 去自环、两个 flow 方向、batch 及空输入逻辑。

## 验收口径与边界

任务文字指定 CPU torch_cluster 近邻集合，而附带测试在 FP16 下按特征
顺序逐次 half 舍入，两者已证明存在不同集合。当前依任务书第 8 节
以原装 CPU torch_cluster 1.6.3+pt27cpu 的输出进行开发自测，请评审确认
最终验收口径；原题
附件不改动并单独标注冲突。c10 已去除额外的 k<=100 限制：大 k
改为动态 Top-K 状态，要求 k<=查询所在 batch 的 N，受实际可用显存限制。

# 详细设计

## 算子分析

欧氏距离以平方距离排序。FP16 实际运算定义为：

```text
s = half(0)
R(v) = round_half_rn(v)
按四个特征一组:
    对组内每个 i: d[i] = R(y[i] - x[i]); p[i] = R(d[i] * d[i])
    group = R(R(R(p[0] + p[1]) + p[2]) + p[3])
    s = R(s + group)
剩余 0..3 个特征: s = R(s + R(R(y[i] - x[i]) ** 2))
```

每一步均显式使用 RINT 转换，累加器保持半精度。分组与上游
nanoflann L2_Adaptor 表达式一致，没有用 FP32 累加、任意树形归约
或范数展开替代此运算。FP32 L2 保留相同四项分组；编译选项
`-ffp-contract=off` 仅施加到 knn_kernel，不影响其他算子。
余弦距离采用 FP32 `1-dot/sqrt(norm_x2*norm_y2)`；零范数时置距离为 1。
L2 等距时采用 CPU 树查询访问次序；cosine 等距按较小 source_index。

## Host 侧设计

Python 处理空输入、1D、连续化、batch_size 推断及 bucketize，传递当前
NPU stream。C++ 检查 device、dtype、维度、k 和 batch 指针，分配输出，
用设备 guard 在对应 NPU 启动。batch 指针复制到 CPU 只用于合法性检查，
点坐标不回 CPU，距离与选择均在 NPU 完成。

核数来自平台 AIV 数，本设备实测 56，少量查询时限制为不超过 M。
host 按 k 容量 1/4/8/16/32/64 分派。F=3/16/32 且容量不超过 32
选择缓存查询版本；其他维度使用运行期循环，不限制为性能表中的形状。
k>64 时分配当前 NPU 上的 M×k FP32 Top-K 距离状态，启动 GM 状态模板；
同 stream 分配与启动遵循 PyTorch allocator 的异步生命周期，已回归
8 次连续调用并立即 clone 消费结果。没有额外的 CPU 距离路径。

## Kernel 侧设计

每核的 SIMT VF 固定 256 线程，`LAUNCH_BOUND` 与 `VF_CALL` 一致。
查询按核划分连续区间；线程以 256 步长领取查询。每个查询独立执行：

1. 二分 ptr_y 定位 batch 并读取对应候选区间。
2. 小 F 版本缓存查询；cosine 计算一次查询范数。
3. 顺序扫描区间内所有候选，按指定数值规则计算距离。
4. 维护本线程有序 Top-K。先比距离，平局按 CPU 树访问顺序比较；
   未优于末位时直接跳过，否则插入并后移元素。
5. 写回 `[query, neighbor]`，不生成 M×N 距离矩阵。

L2 扫描前，在同一 stream 顺序启动根包围盒初始化和树分区 kernel。
树的分区规则来自 torch_cluster 捆绑的 BSD nanoflann，叶子容量为 10，
两阶段 planeSplit 保留原装置换顺序。各 batch 独立构建；每 batch
一个 256 线程块。通常前 7 个 FIFO 节点由全部线程协作；有效建树维度
<=3 时，batchN>=8192 用 31 节点，>=16384 用 63 节点。其余前沿中的
不相交节点独立处理，无核间自旋。FP16 的 `(1-EPS)` 舍入为 1，
原 CPU 严格比较使切分轴保持为 0，因此只需第一维包围盒；FP32 保留
全部维度。等距点在同叶时比较置换位置，否则查找叶子的最近公共祖先，
以该查询对两个切面的比较决定先访问哪一侧。不把较小索引误作 CPU 顺序。
所有点坐标、置换与树构建均在 NPU 完成，未使用 CPU 求邻居或建树。
树规则与 grouped-four 的 CPU 诊断在 68/68 项中匹配原装 wheel 的
集合与顺序；该证据不等于任意输入下 KD-tree 舍入剪枝的形式化证明，
所以完整 NPU 测试继续使用原装 wheel 严格校验。

顶层协作只对包围盒和分区做并行化，距离算术不改。协作分区统计满足
`<cut`（第二阶段 `<=cut`）的总数，在该边界左侧收集不属于左侧的
位置，右侧收集属于左侧的位置，按左位置升序与右位置降序配对交换。
这复现原 two-pointer 交换，而不是任意稳定分区。630 项 CPU-only
审计确认两阶段各自的完整置换与分界均一致。8 KiB UB 保存线程局部
min/max、计数与前缀位置；GM 临时位置列表复用本 batch 预留节点区
最后 `2*batchN` 个 int64。prefix7/31/63 最多分配 15/63/127 节点，
即 120/504/1016 个字段；对应 scratch 最低起点分别为
154/114688/229376 个 int64，均与活跃节点不重叠。后续前沿阶段
不再读这些列表，节点分配可覆盖它们。
各前沿通过原子计数分配孩子 ID，发布完毕后块内同步，再读取下一
前沿边界并再次同步；避免快线程提前修改慢线程尚未读取的边界。

协作 min/max 使用相邻连续区间的二叉归约，等值保留较早位置，连同
signed zero 的位模式也保持不变。计数做整数归约，错误位置列表的
前缀采用块内并行 inclusive scan 后减去本线程计数得到 exclusive
offset；每层邻居读取后、覆盖前和写入后均有块内屏障。480 项 CPU
探针对浮点位模式和整数前缀严格一致；距离累加未做这种并行归约。
FP32 选定切分维后复用该维已计算的 min/max；常量范围未选中维度时
保留原 Range 回退。输入与置换在两次计算之间不变，因此不改变切分。

计算复杂度为最坏 `O(M*N*(F+k))`（分 batch 后按各 batch 求和）。
输出空间为 `O(M*k)`；小 k 每线程状态 `O(KMax+FeatureCache)`。大 k
使用 `O(M*k)` GM 距离 workspace 与输出 col 存储索引，每个线程独占
对应查询切片；length 保证仅读取已由先前插入初始化的槽位。没有额外的
M×N 候选距离表、核间自旋、卡间通信、持久答案缓存或近似搜索。
额外树存储：最多 2N 节点，每节点 8 个 int64，另有 3N int64
置换/逆置换/叶子索引；浮点包围盒为 `2N*(2*bbox_features+2)` 个
float，FP16 的 bbox_features=1，FP32 为 F。分配、构建与查询都计入
完整 API 性能，不允许把树在计时区间外预构建或跨调用缓存。
寄存器/局部内存具体分配尚未被本机可读反汇编或 msprof 完整证实，
因此不把 wall-clock 改善表述为某种已确认的硬件 bound 消除。

## 最终自测证据

c18-prefix63 的完整验收运行 `taskbook-acceptance-NiCYZWxn` 在同一份源码及
动态库上依次通过 300/300 正确性（233.85 s）、原题 64/64 性能和辅助
64/64 性能。阶段退出码为 0，16 项源码与二进制前后 SHA256 全部一致。
两套最小性能比分别为 0.482076 / 0.503342，均高于任务书要求的 0.45。

最紧的 N=16384、F=3、k=8、FP32 原题完整 API 耗时为 19.638 ms，
上限为 9.467/0.45=21.037778 ms。辅助独立测量为 18.808278 ms。
完整参数、64 项表和截图见提交包自测报告，不用关键项代替全量结果。

每项比较真实 CPU 标杆的完整查询边集合。300 项中保留原有 194 项，新增
106 项 F3、batch/graph/stream、大树及协作前缀阈值测试。原题性能脚本
未改动。历史候选的失败摘要保留在 `candidates.jsonl` / `benchmark.csv`，
不用于拼接或抬高本版本成绩。

## 支持硬件与限制

torch_npu 2.7.1.post8、Python 3.12.13；不声称 A2/A3 或其他版本已验证。

# 可维可测分析

## 精度标准和性能标准

原题文件保留不改。当前 `test_knn.py` 使用真实 CPU wheel 检验
L2/graph 的全部近邻集合，cosine 采用独立 CPU double 标杆；覆盖两种
dtype、batch、k 边界、等距、stream 和大规模等 300 项，不接受换邻居。

同一 wheel；20 项串行/并行输出逐元素一致。该调度只用于生成标杆，
NPU 仍是一次完整形状调用，性能计时脚本不改，不保存或复用答案。
真实 CPU 标杆与原题 golden 冲突单独存证。

每个性能项采用 20 warmup、100 次完整 API 调用、区间外同步的 wall-clock
平均耗时，独立要求 `reference_ms/measured_ms >= 0.45`。原题脚本和固定
种子的 JSON helper 分开跑、分开记录；不拼接不同候选结果、不选最好轮。
source、CMake、两个动态库 SHA256 与每个不可变运行目录绑定。
